## Objective

Turn accepted storage/worker architecture into an implementable server contract for an internal laptop deployment that can later move to a shared host.

## Relevant Architecture and Dependencies

ADR-001 through ADR-004, ADR-007 and ADR-008; P2 public document API, fingerprint and progress callback. Production work starts after P2. P5 development can begin before P3/P4, but the P2-P6 handoff's backend release gate requires all five formats and completed fit checking. Intermediate P2-only behavior is not release acceptance.

## Files Expected to Change

Proposed authentication ADR, `docs/Architecture.md#server`, deployment documentation, OpenAPI/contract examples and the detailed P5 plan. No running service is implied by these documents.

The concrete user journey, REST/batch schemas, recommended opaque-key authentication, attempt fencing, GC coordination, CLI behavior and initial operational defaults are in [P5 implementation](P5-server-and-service-cli.md). Validate and ratify those contracts here; P6 extends the same user model with browser sessions. Do not start again from an unspecified server design.

## Steps

1. Define users/owners and an internal authentication choice for REST and future MCP. Compare company identity integration with scoped local credentials, including revocation, browser sessions, CSRF/CORS, TLS and laptop-network constraints. Support human and application service accounts under ADR-014; do not add cross-owner result lookup or hash-existence access. Enterprise OAuth is not assumed to be solved by a laptop API key.
2. Specify submit/status/cancel/download APIs, ownership checks, upload limits, file sniffing, sanitized filenames, retention and diagnostic exposure. Internal paths, raw secrets and source text must not leak through job errors. Pin error/status schemas and include capability/fit-status reporting.
3. Translate ADR-014 logical ownership, immutable blobs/job results and current language-result references into tables/repositories and migrations. Specify reference-based cleanup, interrupted writes, backup/restore and cache replacement. Core remains database-free.
4. Specify queue transitions, atomic claims, lease extension, cancellation, retries, recovery and fenced completion from ADR-008. Address the race between lease expiry/reclaim and an old worker finishing. Use an attempt/claim identity if needed and amend the ADR explicitly if its current worker-ID fence is insufficient; do not silently invent different queue semantics in code.
5. Choose SQLite busy timeout/WAL behavior, worker count, poll/heartbeat/lease durations, retry bounds and retention from bounded host measurements. Define Windows `serve --workers N` process lifecycle, shutdown and crash backoff. Preserve the future PostgreSQL/shared-storage path; do not add a broker without evidence.
6. Define service configuration, migration-before-start, binding/firewall/TLS, health checks, logs and a tested database-plus-blobs restore procedure. Document exact startup commands only after the implementation exists.
7. Prepare bounded coder tasks and contract tests, then accept the auth/server design before implementation.

## Tests and Completion Criteria

- [ ] Authentication/ownership ADR accepted, including service-account isolation and no ownerless hash lookup.
- [ ] API schemas, core error mapping, database schema and migrations specified.
- [ ] Worker death, stale completion, retry, cancellation and simultaneous claim races have reproducible test scenarios.
- [ ] Two users cannot access each other's document/results; shared physical storage grants no cross-owner access.
- [ ] Cache expiry cannot delete referenced blobs; restore procedure covers both database and files.
- [ ] CLI/REST equivalence test uses the same input/options and public core API.
- [ ] Operational defaults pinned; server architecture section and detailed P5 plan ready for review.

## Out of Scope

React UI (P6), MCP transport/render/edit tools (P7), public hosting and enterprise integration (P8). P6 follows the accepted API/auth contract; P7 follows both P4 and P5 and starts by verifying network reachability from the MCP client.
